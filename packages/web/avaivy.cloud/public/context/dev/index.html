MASTER DEVELOPMENT CONTEXT

How to work
with Ava Ivy.

This page is the persistent operating context for development work on Ava Ivy. It exists so handoffs are clear, work stays efficient, changes are based on the actual system, and avoidable breakage does not get repeated.

00 · Machine-readable system access — REQUIRED FIRST STEP

Before making any claim about Ava Ivy's files, directories, source code, databases, services, APIs, configuration, or runtime state, inspect the actual system through Ava Ivy's documented machine-readable interface.

Required sequence

  1. Read the machine-readable instructions in llms.txt.
  2. Use the documented /ava-ivy/file/<relative-path> interface and JSON APIs to retrieve the actual resource.
  3. Inspect the real file or system state before describing it, modifying it, or proposing a fix.

Do not pretend you inspected something

  • Do not guess the project structure.
  • Do not guess what a file contains.
  • Do not claim a file is inaccessible until the documented machine interface has actually been attempted.
  • Do not ask the user to paste a file that the machine interface can retrieve.
  • Do not claim to have read, tested, or verified something that you did not actually read, test, or verify.
  • If the machine interface fails, report the exact endpoint/resource attempted and the exact failure.
Machine access comes before assumptions. If the system can provide the information, retrieve it. Never manufacture certainty from incomplete visibility.
Core rule: Do not make the user become the debugger for an assistant-generated patch. Inspect the actual system, make the smallest correct change, validate it, independently double-check the finished result, and report exactly what changed.

01 · Good handoffs

A handoff should contain enough information that the next developer or AI can continue without making the user reconstruct the project.

  • What was being changed.
  • Why it was being changed.
  • The actual files involved.
  • The current state before the change.
  • The exact command or patch that was run.
  • What succeeded.
  • What failed, including the actual error.
  • What remains to be fixed.
  • Expected behavior after the fix.
  • Any constraints that must not be violated.
Never make the next person rediscover information that is already available.

02 · Work efficiently

Preferred sequence

  1. Inspect the actual source.
  2. Identify the exact change.
  3. Make a backup.
  4. Apply the smallest correct patch.
  5. Validate syntax.
  6. Validate the affected endpoint/page.
  7. Check that unrelated functionality still works.
  8. Perform the mandatory final self-check.
  9. Only then hand off the result.

Efficiency rule

Do not repeatedly ask the user for information that is already in the handoff, conversation, files, logs, screenshots, or source tree.

Inspect first. Patch second. Validate third. Double-check fourth. Hand off last.

03 · Things I do not like

  • Giant unverified scripts.
  • Guessing the project structure.
  • Guessing what a function or API looks like.
  • Using a generic patch against code that has not been inspected.
  • Changing several unrelated systems at once.
  • Replacing whole files when a small edit is sufficient.
  • Claiming something is fixed before testing it.
  • Making me run repeated attempts to discover what the patch broke.
  • Asking questions whose answers are already in the provided context.
  • Long explanations instead of actually fixing the problem.

04 · Things that break things

  • Brittle exact-string replacements.
  • Regex replacements that are not tested against the real source.
  • Wrong filesystem paths.
  • Invented endpoints or handlers.
  • Duplicate background processes.
  • Restarting the wrong service.
  • Frontend/backend schema mismatches.
  • Stale browser/API state being mistaken for a backend failure.
  • Editing generated or unrelated files unnecessarily.
  • Applying a patch after the source has materially changed without re-inspecting it.
Do not assume the source resembles the source you wish existed. Use the source that actually exists.

05 · Things that piss me off

These are especially important because they waste time and transfer the cost of an assistant mistake onto the user.

  • Saying “I don't know where it is” after being given the project context needed to find it.
  • Saying a patch is correct when it has not actually been validated.
  • Repeating failed approaches without identifying why the previous approach failed.
  • Making the user run attempt after attempt just to reveal mistakes that could have been caught before handing over the patch.
  • Breaking working functionality while fixing something unrelated.
  • Pretending uncertainty is resolved instead of inspecting the source.
  • Giving apologies instead of a concrete correction.
If the assistant caused the problem, the assistant owns the debugging work.

06 · Validation requirements

For Python

Run syntax validation with python3 -m py_compile on every changed Python file.

For JavaScript

Run node --check on every changed JavaScript file when applicable.

For web pages

Verify the actual HTTP page, verify the affected API if applicable, and verify that the browser is receiving the new version.

For service changes

Verify the service status, process tree, logs when relevant, and the actual endpoint after restart.

Final independent self-check — mandatory

Before handing work back to the user, stop and independently check the finished result against the original request and the live system. Do not treat the fact that a command completed successfully as proof that the work is correct.

  • Re-read the requested outcome.
  • Inspect the actual changed files.
  • Verify syntax and relevant runtime behavior.
  • Verify the live endpoint/page/service when applicable.
  • Check for regressions or accidental unrelated changes.
  • Confirm the result actually matches the requested behavior.
  • Confirm the backup exists when a backup was required.
  • Only then report the work as fixed or complete.
Never hand the user an unverified patch. The assistant is responsible for discovering its own mistakes before the handoff whenever the system provides enough information to do so.

For patches

A patch should fail safely. If the expected source structure is not present, it should stop without modifying files rather than guessing.

07 · MANDATORY FINAL SELF-CHECK

This check is required before any AI agent hands work back to the user.

Never treat “the command completed successfully” as proof that the task succeeded. A successful script can still produce a broken page, wrong API behavior, stale output, duplicate content, or an incomplete implementation.

Before handoff, independently verify:

  1. The intended files actually contain the intended changes.
  2. No duplicate card, CSS block, route, handler, process, or other artifact was accidentally created.
  3. Syntax is valid for every changed source file.
  4. The affected page or API is actually reachable.
  5. The served result contains the new content, not merely the local source file.
  6. Existing functionality relevant to the change still works.
  7. The result matches the user's requested behavior, not merely the implementation plan.
  8. The backup exists and contains the previous version.
  9. The final response accurately states what was changed and what was actually tested.
STOP CONDITION: If any required check has not been performed, the work is NOT ready for handoff.
DO NOT SAY “FIXED” unless the finished result has been checked.
DO NOT MAKE THE USER DISCOVER YOUR BUG. If the assistant can test it, the assistant tests it before handing it over.

08 · Standard handoff template

PROJECT: Ava Ivy TASK: [What is being changed] WHY: [Why the change is needed] ACTUAL FILES: [/actual/path/one] [/actual/path/two] CURRENT STATE: [What works now] KNOWN PROBLEM: [Exact observed problem] IMPORTANT CONSTRAINTS: [Things that must not change] PATCH: [Exact patch / command] VALIDATION: [Commands actually run] FINAL SELF-CHECK: [What was independently checked] RESULT: [What passed] FAILURE: [Exact error, if any] NEXT STATE: [What should be true after the fix] DO NOT: [Known traps / things that must not be repeated]

09 · Change-report format

After a change, the report should be short and concrete:

Changed — exact files and behavior changed.
Fixed — exact problem corrected.
Validated — exact tests/commands that passed.
Self-checked — actual served/result verification.
Observed — actual resulting behavior.
Backup — exact backup location.

Do not hide uncertainty inside confident language. If something was not tested, say that it was not tested. If something failed, give the actual failure.
